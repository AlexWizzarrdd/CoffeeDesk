1. Авторизация и регистрация

1.1. Регистрация пользователя

POST
/api/auth/register/

Тело запроса:
{
  "email": "test@mail.com",
  "password": "123456789",
  "first_name": "Иван",
  "last_name": "Иванов",
  "phone": "+79991234567"
}

Ответ:
{
  "id": 7,
  "email": "test@mail.com",
  "first_name": "Иван",
  "last_name": "Иванов",
  "phone": "+79991234567",
  "role": "employee",
  "is_approved": false,
  "is_active": false
}

Логика:
	•	зарегистрированный пользователь не может войти, пока менеджер не подтвердит его.
	•	is_active=false блокирует вход.
	•	Фронтендер должен выводить сообщение:
“Ваша учётная запись ожидает подтверждения менеджером”

1.2. Авторизация (логин по телефону)
POST
/api/auth/login/

Тело запроса:
{
  "phone": "123456789",
  "password": "123456789"
}

Ответ:
{
  "refresh": "....",
  "access": "...."
}

Логика:
	•	После успешного логина фронт должен сохранить токены:
	•	localStorage.access
	•	localStorage.refresh
	•	И делать редирект в личный кабинет: /profile

1.3. Личный кабинет

GET
/api/auth/me/

Ответ:
{
  "id": 5,
  "email": "test@mail.com",
  "first_name": "Иван",
  "last_name": "Иванов",
  "phone": "+79995551234",
  "role": "manager",
  "is_approved": true,
  "is_staff": true
}

Логика:
	•	Если токена нет → редирект на /login
	•	Если токен есть, но сервер отвечает 401 → обновить токен или разлогинить

2. Управление пользователями (доступно менеджеру)

2.1. Получить список всех пользователей

GET
/api/manager/users/
[
  {
    "id": 1,
    "email": "test@example.com",
    "first_name": "Тест",
    "last_name": "Тестов",
    "phone": "+79990000000",
    "role": "employee",
    "is_approved": false,
    "is_active": false
  },
  ...
]

Логика фронтенда:
	•	Отображать таблицу пользователей
	•	Если is_approved=false → показывать кнопку «Подтвердить»
	•	Если is_approved=true → показывать статус «Подтверждён»

2.2. Подтвердить учётную запись
PATCH
/api/manager/users/<id>/approve/

{
  "is_approved": true,
  "is_active": true
}

Ответ:
{
  "id": 1,
  "is_approved": true,
  "role": "employee"
}

Логика:
	•	После подтверждения → обновить список (refresh)
	•	Пользователь после этого может войти

3. Роли пользователей

Список ролей:

Роль       | Описание
-----------|-------------------------------------------------------
employee   | обычный сотрудник
manager    | имеет доступ к списку пользователей и подтверждению их
admin      | тот же менеджер, но может назначать роли другим

Фронтенд должен:
	•	хранить роль после GET /me/
	•	скрывать элементы UI, если роль не подходит
пример:
	•	менеджеру показывать /users
	•	сотруднику — нет

4. Как фронту работать с токенами

Access token хранится в:
localStorage.access

Refresh token хранится в:
localStorage.refresh

При каждом запросе фронтенд должен отправлять заголовок:
Authorization: Bearer <access>

Если access истёк (401):
	•	автоматически попытаться обновить токен через refresh
	•	если refresh тоже истёк → разлогинить
